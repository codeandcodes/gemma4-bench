LongBench Pro — Gemma 4 26B-A4B-it benchmarks

Per-quantization & per-engine evaluation of Gemma 4 26B-A4B-it on LongBench Pro (bilingual long-context benchmark: 1,500 samples, 11 primary tasks, 25 secondary tasks, contexts 8K–256K tokens by Qwen tokenizer). Hardware: single NVIDIA RTX Pro 6000 Workstation Edition (96 GB).
Live dashboard: codeandcodes.github.io/gemma4-bench/dashboard.html — cross-quant comparison tables on the same 500-item subset. Schema reference for downstream tools: SCHEMA.md.

TL;DR

  • Most-quantized still works. Bartowski Q8_0 scores 0.691, IQ4_XS 0.641, IQ2_M 0.577 on the 500-item English ≤64K subset (mean of Pro's official task metrics, empties counted as 0).
  • BF16 (the reference) reaches only 0.652 via vLLM. It currently sits below Bartowski Q8 (0.691) and is essentially tied with IQ4_XS (0.641). Physics says BF16 should be ≥ Q8 at fixed inference conditions, so something else is varying. This is the central puzzle this folder investigates — see The BF16 puzzle.
  • Empty rates climb sharply with aggressive quantization. BF16 (vLLM) has 0% empty. Q8_0 (llama.cpp) 3.2%. IQ4_XS 9.6%. IQ2_M 15.2%. Most of IQ2's apparent weakness is "failed to produce a response" not "produced a wrong one" — see scored-only view.
  • 2-bit is viable. IQ2_M is 11 GB on disk (vs 27 GB for Q8_0) and loses only ~3.4 pp absolute vs BF16, ~11 pp vs Q8_0. For memory-constrained deployments where the alternative is a smaller model, IQ2_M of a 26B beats running, say, a 4B at BF16.

Methodology

Inference harness

All runs use the official LongBench Pro inference harness (main.py --only_infer) with small additive modifications for streaming-based metric capture (see patches/). The harness sends one item at a time to an OpenAI-compatible endpoint. Identical command-line shape across all configs, only the model name / endpoint URL changes: 

python main.py --only_infer \
  --model_manager openai \
  --model_name <CONFIG> \
  --tokenizer_path model/Tokenizers/qwen \
  --dataset_path dataset/longbench_pro_en_le64k.json \   # 500-item subset
  --context_max_length 100000 \                          # or 170000 for llama.cpp
  --url http://127.0.0.1:<PORT>/v1 --api_key dummy \
  --temperature 1.0 --max_new_tokens 32768 \
  --timeout 1800 --max_tries 5 --time_sleep 0.0 \
  --bon_num 1 --n_proc 4 \
  --extra_body '{"top_p": 0.95, "top_k": 64,
                 "chat_template_kwargs": {"enable_thinking": true}}'

Sampling parameters

temperature=1.0, top_p=0.95, top_k=64 — Gemma 4's recommended defaults. Same across all configs to control for sampler drift.

llama.cpp server config

llama-server \
  --model <GGUF> --ctx-size 1048576 -np 4 -ub 4096 \
  --temp 1.0 --top-p 0.95 --top-k 64 \
  --jinja --spec-type ngram-cache

4 parallel slots × 262K per-slot context = 1M token total KV budget. --spec-type ngram-cache is n-gram speculative decoding (small win, no extra model). -ub 4096 ups the physical batch from the default 512 → faster prefill on long inputs. Built from upstream ggml-org/llama.cpp (commit current as of run date).

vLLM server config

vllm serve google/gemma-4-26B-A4B-it \
  --dtype bfloat16 --max-model-len 131072 --max-num-seqs 4 \
  --gpu-memory-utilization 0.92 --enable-prefix-caching

4 parallel sequences, 128K per-sequence max context. enable_thinking passed in the request body to trigger Gemma 4's <|think|> system-turn injection.

Why context_max_length=100000 (Qwen tokens) for vLLM, 170K for llama.cpp?

Pro's dataset bucketing was done with the Qwen tokenizer. The model runs with Gemma's tokenizer. For English content the ratio is close to 1.0×, but Gemma can expand to ~1.3× on Chinese (irrelevant for the English-only subset but the same code path is used in the full runs). 100K Qwen × 1.3 ≈ 130K Gemma, fits in vLLM's 131K. The llama.cpp runs target a 262K-per-slot context so use 170K Qwen with the same safety margin.

The 500-item English ≤64K subset

Pre-filtered slice of the full Pro dataset: language == "English" AND token_length ∈ {8K, 16K, 32K, 64K}. Exactly 125 items per length bucket, all 11 primary tasks represented, distributed across all difficulties. File: dataset/longbench_pro_en_le64k.json (68 MB; also vendored into results/iq2_m/dataset_subset_english_le64k.json for the Unsloth IQ2 run). This subset was chosen to keep wall-time manageable for repeated runs (~3–4 h each) and to focus on the regime where the model performs best (long context is genuinely hard for everything we tested).

The BF16 puzzle (engine vs precision)

The surprising finding: BF16 served via vLLM scores 0.652, well below Bartowski Q8_0 served via llama.cpp at 0.691. Quantization can't add quality — Q8 is lossy compression of BF16. So at identical inference conditions, BF16 should be at least as good as any quant. Something else must be varying.

The variables we know differ between the two:

Variable BF16 (vLLM) Q8_0 (llama.cpp)
Precision bfloat16 int8 (imatrix-calibrated)
Inference engine vLLM llama.cpp
Chat template HF chat_template.jinja GGUF-bundled Jinja
Thinking trigger explicit chat_template_kwargs.enable_thinking=true → <|think|> injected at system turn no explicit flag; model thinks via training default
Tokenizer encoding HF tokenizer.json GGUF-converted tokens
Sampler implementation vLLM's top_p/top_k llama.cpp's top_p/top_k

Any of those rightmost-column items can shift scores at the ±0.05 level we're seeing. We can't say from this matrix alone how much is precision and how much is everything else.

The isolating experiment — results in

We ran BF16 served via llama.cpp using Bartowski's BF16 GGUF on the same 500 items. Combined with the existing runs we now have:

Comparison Δ What's held constant
BF16-vLLM vs BF16-llamacpp +0.012 precision (BF16)
BF16-llamacpp vs Q8-llamacpp (Bart) −0.051 engine (llama.cpp), source (Bartowski GGUF)

The engine effect is small (+0.012). Removing the engine variable doesn't close the BF16 vs Q8 gap — if anything, llama.cpp's BF16 is even lower than vLLM's. So engine drift isn't the explanation.

The precision effect is real and substantial: −0.051. On the same engine, same source (Bartowski's GGUF family), same items, Q8_0 beats BF16 by 5 percentage points. That's the part that shouldn't happen if quantization is purely lossy. Possible explanations:

  1. imatrix-calibrated Q8 preserves task-relevant behaviors better than vanilla BF16 inference. Bartowski's Q8_0 uses imatrix calibration that allocates more bits to weights with high activation on the calibration data. If that calibration happens to emphasize the kinds of patterns Pro tests (structured output formatting, instruction following, the [Answer] marker convention), the quantized version effectively gets a small task-specific tilt that BF16 doesn't.
  2. llama.cpp's BF16 code path may be less battle-tested than its quant kernels. The Q4/Q5/Q6/Q8 code paths in llama.cpp see far more usage and tuning than the BF16 path. Subtle numerical issues in rare BF16 ops could account for a few percent.
  3. The model may have been trained or distilled with quantization in mind (Gemma 4 ships with NVFP4 variants and has a small "assistant" MTP head — both suggest the team thinks about quantized deployments first-class). If the BF16 numerical surface was treated as a means-to-an-end rather than the canonical inference target, BF16 inference can be slightly off-policy compared to what the imatrix- calibrated quants reconstruct.
  4. Pro's metric is sensitive to format compliance. The scorer finds [Answer] markers and parses what follows. Empties score 0. BF16-llamacpp has 7.6% empty (38/500); Q8-llamacpp has 3.2% (16/500). Half of the 5-pp gap could be accounted for purely by Q8 producing fewer degenerate / empty outputs. The scored-only view below quantifies this.

Scored-only (empty rows excluded):

Config n scored Mean (scored)
BF16 (vLLM) 500 0.652
BF16 (Bartowski GGUF, llama.cpp) 462 0.693
Q8_0 (Bartowski GGUF, llama.cpp) 484 0.714

With empties excluded, the BF16 vs Q8 gap closes from −0.051 to −0.021 — still material (~3% relative), but ~60% of the original gap was driven by reliability, not accuracy. The remaining ~2 pp is the "quantization helps" effect that needs one of the explanations above.

What this is NOT

It is not "quantization adds information." Quantization can only preserve or destroy. What the evidence suggests is that vanilla BF16 inference is not the optimal use of these weights for this benchmark, and that imatrix-calibrated Q8 produces a numerical regime that empirically scores better on Pro.

Practical takeaway

Q8 GGUF (Bartowski calibration) is the best per-GB choice on this hardware — better than running BF16, at half the disk and KV bandwidth. If you've been defaulting to BF16 as the "reference" quality, this is evidence to switch to imatrix-calibrated Q8 in practice.

Why batching only helps modestly (bandwidth analysis)

Decode is memory-bandwidth-bound on this hardware. Per token, the GPU reads:

  1. Model weights — shared across the batch, read once for all sequences.
  2. KV cache — not shared, each sequence has its own.

Gemma 4 26B-A4B is an MoE model with ~4B active parameters per token. That makes the "weight read" cost per token small (~4 GB at Q8), while the per-stream KV cache at long context is large (~10 GB at 262K). At batch=4 the KV reads scale linearly (40 GB) but weight reads only go up modestly due to MoE expert routing across the batch (~6–8 GB). Total per batch step ≈ 47 GB. At 1.5 TB/s effective bandwidth that's ~32 ms per step → ~125 t/s aggregate.

Observed: 115–130 t/s aggregate. Theory matches within 10%.

This means: 4-way batching gives roughly the same aggregate throughput as 1-way at this context length. Per-token decode does NOT scale with parallel slots when KV cache reads dominate. The 4-way batching does still help prefill (compute-bound, kernel batching), which is why we still see ~38% wall-time improvement vs single-stream.

For a different model regime (e.g. dense 26B at short context), the weight-to-KV ratio flips and batching scales near-linearly. For MoE-A4B-at-long-context (this benchmark), it doesn't.

Caveats & methodology smudges

Empty predictions count as 0.0

Per Pro's official scoring, items where the model fails to produce a non-empty response are scored 0.0 and included in the mean. This is the right call for production reliability comparisons but penalizes flaky quants. A "scored-only" view (excluding empties) significantly closes the IQ2_M gap:

Quant Empty Official mean Scored-only mean
BF16 (vLLM) 0/500 0.652 0.652
Q8_0 (Bart) 16/500 0.691 0.714
IQ4_XS (Bart) 48/500 0.641 0.710
IQ2_M (Bart) 76/500 0.577 0.680

So IQ2's apparent weakness (0.577) is largely a reliability issue (15% empty), not an accuracy issue (0.680 when it does respond). Different deployments will weight these differently.

vLLM doesn't separate reasoning_content from content

When llama.cpp serves a thinking model, it parses out <|think|>…<|/think|> blocks into a separate reasoning_content stream. vLLM puts everything in content. Both produce text that the Pro scorer can parse (it looks for [Answer] or [答案] anywhere in the prediction). But the data shape differs:

  • llama.cpp rows have thinking field populated with the reasoning trace (median ~13K chars).
  • vLLM rows have thinking field empty; the reasoning is mixed into prediction.

For downstream analysis that wants the "raw model output", concatenate thinking + "\n" + prediction for llama.cpp rows or just use prediction for vLLM rows.

Unsloth quants used the GGUF-bundled chat template, not the HF one

The GGUF chat template has minor differences from HF's chat_template.jinja (e.g., the GGUF version is what Unsloth embedded during conversion). For the full Unsloth runs (1500 items), this means there's a small additional axis of variation between Unsloth and Bartowski numbers beyond the calibration recipe difference. The Bartowski runs in this dashboard avoid that by using llama.cpp's --jinja + GGUF template consistently.

vLLM can't load Gemma 4 GGUFs

transformers (which vLLM uses to parse GGUF metadata) does not support the gemma4 architecture for GGUF loading. We attempted to run Bart-Q8_0/IQ4_XS/IQ2_M on vLLM directly and hit ValueError: GGUF model with architecture gemma4 is not supported yet. So the engine-vs-precision matrix has gaps in the vLLM column. The BF16-llama.cpp run (using Bartowski's BF16 GGUF) is the cleanest within-engine reference we can produce while waiting for upstream support.
